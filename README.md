ToolForge discovers the tools in this repository and serves published, enabled tools to MCP clients. New catalogs start with shared Python configuration and no tools.

## Quick start

1. In ToolForge, create a tool and open its source.
2. Write a Python function that accepts client inputs and returns a value. Give it a docstring and name it in a literal, one-item `__all__` list.
3. Choose Publish in ToolForge to activate that version. Saving in the editor or committing in its workspace leaves a draft.

For example, `tools/greet/tool.py`:

```python
__all__ = ["greet"]


def greet(name: str) -> str:
    """Return a greeting for a name."""
    return f"Hello, {name}!"
```

| Python                           | MCP                       |
| -------------------------------- | ------------------------- |
| Exported function name (`greet`) | Tool name                 |
| Docstring                        | Tool description          |
| Function signature               | Input schema              |
| Return value                     | Result sent to the caller |

## Repository layout

| Path                      | Purpose                                   |
| ------------------------- | ----------------------------------------- |
| `tools/<tool-id>/tool.py` | Tool entrypoint                           |
| `tools/<tool-id>/`        | Supporting code and data for that tool    |
| `pyproject.toml`          | Dependencies shared by all tools          |
| `requirements.lock`       | Matching lock file generated by ToolForge |

The tool ID is its directory name. Keep it stable when changing the code. Each tool's sandbox shows its own directory and the shared Python files, with this README at the catalog root for reference.

## Work with Git

A Git remote is optional. If ToolForge has a repository and branch configured:

- Edit tools at `tools/<tool-id>/tool.py`, using the export contract above.
- Commit changes to the configured branch. ToolForge syncs it and makes valid, enabled tools available to the running instance.
- Edit this README in a normal Git checkout.

MCP clients connect to the running ToolForge instance. A Git clone does not serve MCP requests.

## Dependencies and secrets

Edit the shared `pyproject.toml` in ToolForge, then Publish to generate a matching `requirements.lock`.

> [!WARNING]
> Changing `pyproject.toml` alone can leave the lock out of sync and prevent activation. Do not hand-edit `requirements.lock`.

In ToolForge, open [CONFIGURATION → Server → Environment variables](http://localhost:3000/configuration/server#environment-section-title) to set API keys and other runtime values. ToolForge passes them to the tool process without storing them in Git. Keep credentials out of tool source, supporting files, and this README.

## Connect via MCP

1. In ToolForge, open [CONFIGURATION → Server → MCP](http://localhost:3000/configuration/server#mcp-section-title) and choose Copy MCP endpoint. The instance's `/mcp` endpoint uses Streamable HTTP.
2. Configure your client to send a Microsoft Entra bearer token for the instance's tenant and audience. It must include the delegated scope or application role shown under Required permission in the same panel.

### Check with MCP Inspector

The [MCP Inspector CLI](https://github.com/modelcontextprotocol/inspector/blob/main/clients/cli/README.md#remote-servers) requires [Node.js 22.19 or newer](https://github.com/modelcontextprotocol/inspector/blob/main/package.json). With a valid access token already in `TOOLFORGE_ACCESS_TOKEN`, replace the URL below with the endpoint you copied:

```bash
npx @modelcontextprotocol/inspector --cli "https://<instance-host>/mcp" --transport http --method tools/list --header "Authorization: Bearer $TOOLFORGE_ACCESS_TOKEN"
```

This lists the tools available to your identity. An empty list is expected until a tool is published and enabled. Create your first tool in ToolForge, publish it, then run the command again.
